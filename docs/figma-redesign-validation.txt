Figma redesign UI validation
Date: 2026-10-15
Source handoff: docs/figma-design-handoff.json (38 verified routes, 174 desktop/mobile frames)
Spec: tests/e2e/figma-redesign.ui.spec.ts

Scope and safety
The spec intercepts every /api/v1 request in the browser and returns fictional fixtures. No real account password, database record, attendance record, message, or external service is used. The mock login accepts a synthetic-only password string; all mutation endpoints are handled by route fixtures. The photo check posts attendance with no file to prove that a photo remains optional. Mock 403 and 409 replies exercise visible authorization and stale-version feedback.

Responsive coverage
The public home is opened at 320, 390, 768, and 1440 CSS pixels. A guest follows a public article and product detail into a guest cart, supplies synthetic contact data, and receives a no-payment order result. The volunteer inbox, read-only session detail, admin people list, permission editor, and form response detail are checked at 390px for overflow. The route matrix below checks every Figma route at 390px.

Behavior checks
- Public story, article, food catalog, product variant, cart quotation, and guest order; verify the order result states that no payment was collected.
- A multi-role volunteer sees service navigation without management navigation. The mobile menu opens and Escape closes it while restoring focus.
- Course notification filtering and unread count, notification deep link to the course, teacher and location details, and the absence of edit controls for a volunteer.
- Self check-in accepts no photo and sends `mode=self` to a mocked endpoint.
- Admin user list, human-readable permission labels, and human-readable form answers; response detail must not render a raw JSON `<pre>`.
- A mocked 409 stale-role/schedule response and mocked 403 inquiry update are shown to the operator.

Regression boundaries
This spec does not replace existing notification or calendar suites. Keep the existing 6 notification and 20 calendar checks in the normal mocked Playwright run. Do not use the live API/e2e suite against a local or GCP database as part of this validation. The UI suite must run against the local integrated app only after the coordinator reports it available; report the exact Playwright command and result here before treating the redesign validation as complete.
